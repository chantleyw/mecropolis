Mecropolis – Full Project Specification
Sep 20, 2026 · @Chantley
Project Overview
Mecropolis is an AI-powered field and crop tracker for agricultural operations. A farm manager registers fields, plans seasonal crops, logs treatments and pest reports, and advances each season through a structured lifecycle. Weather data from Open-Meteo is fetched automatically at key stage transitions, attaching soil temperature, precipitation, and evapotranspiration snapshots directly to the content.

Workflow Engine: Season Lifecycle
The season document's stage field drives the entire application. Transitions are validated server-side and each can trigger side effects.
State machine
[planning] ---> [planted] ---> [growing] ---> [pre-harvest] ---> [harvested] ---> [review]
                                   ^              |
                                   |              |
                                   +--(reject)----+

Guard implementation
Guards live in src/lib/workflow/guards.ts. Each guard is a pure function:
type Guard = (season: Season, context: TransitionContext) => 
  { valid: true } | { valid: false; reason: string }
The transition API route checks all guards before allowing a stage change. If any guard fails, the response includes the reason and the transition is rejected.
Side effects implementation
Side effects live in src/lib/workflow/effects.ts. Each effect is an async function that runs after a successful transition:
type Effect = (season: Season, transition: Transition) => Promise<void>
Effects are fire-and-forget from the user's perspective (the transition succeeds immediately, the weather fetch happens in the background). If a weather fetch fails, the transition still stands but no weatherSnapshot is created. The stageHistory entry records whether the effect succeeded or failed.
stageHistory audit trail
Every transition appends an entry to season.stageHistory:
{
  "stage": "planted",
  "previousStage": "planning",
  "timestamp": "2026-09-20T10:30:00Z",
  "triggeredBy": "user",
  "weatherFetched": true,
  "weatherSnapshotId": "abc123",
  "notes": "Planted on schedule, soil temp 18C"
}
This gives judges a visible audit trail showing that the workflow is real, not decorative.
Sanity Studio integration
The stage field in the Studio should display as a read-only badge (not a dropdown). Transitions happen through the Next.js frontend, not by editing the field directly. This enforces the guard logic. If someone changes the field directly in Studio, the stageHistory won't be updated and no side effects fire, which is the intended signal that something was done out-of-band.
Optionally, a custom Studio document action can be added to expose "Advance Stage" as a button within the Studio UI itself, calling the same API route. This is a nice-to-have.

Request flow
1. Transition API receives a stage change request.
2. Guards pass. Stage is updated on the Sanity document.
3. Effect function determines which weather call to make based on the transition.
4. Weather wrapper (src/lib/weather/openmeteo.ts) builds the URL and fetches.
5. Response is parsed. A summary object is computed (averages, totals).
6. A weatherSnapshot document is created in Sanity with the raw data and summary.
7. The snapshot's _id is recorded in the stageHistory entry.

Error handling
Open-Meteo is highly available but the app must not break if it's down. Strategy:
• Weather fetch is async, non-blocking. The transition succeeds regardless.
• If the fetch fails (network, API error, malformed response), log the error and record weatherFetched: false in the stageHistory entry.
• No weatherSnapshot document is created on failure.
• The frontend shows "Weather data unavailable" in the timeline for that transition.
• No retries. The user can manually trigger a re-fetch from the field detail page if needed (stretch goal).
Next.js API Routes
All backend logic lives in Next.js Route Handlers under src/app/api/.
POST /api/transition
Advances a season's stage. This is the core workflow endpoint.
Request body:
{
  "seasonId": "season-doc-id",
  "targetStage": "planted",
  "notes": "Optional transition notes"
}
Response (success, 200):
{
  "success": true,
  "season": { "_id": "...", "stage": "planted", "stageHistory": [...] },
  "weatherSnapshot": { "_id": "...", "summary": {...} } | null,
  "message": "Season advanced to planted"
}
Response (guard failure, 400):
{
  "success": false,
  "error": "Guard failed",
  "reason": "plantingDate must be set before transitioning to planted",
  "currentStage": "planning"
}
Response (invalid transition, 400):
{
  "success": false,
  "error": "Invalid transition",
  "reason": "Cannot transition from planning to growing. Valid targets: planted",
  "currentStage": "planning"
}
Logic flow:
1. Fetch the season document from Sanity (with field + crop references expanded).
2. Validate that currentStage -> targetStage is a valid transition.
3. Run all guards for this transition.
4. If guards pass: patch the season document (stage, append stageHistory).
5. Fire side effects (weather fetch, create snapshot).
6. Return the updated season and any created snapshot.
GET /api/weather?fieldId=xxx&start=YYYY-MM-DD&end=YYYY-MM-DD
Manual weather fetch for a field. Used by the frontend for on-demand weather checks.
Response (200):
{
  "forecast": { ...OpenMeteo response },
  "summary": { "avgTempMax": 28.5, "totalPrecipitation": 42.0, ... }
}
Looks up the field's farm coordinates and calls Open-Meteo. Does not create a Sanity document (that only happens through transitions).
POST /api/webhook
Sanity webhook receiver. Triggers when documents change in the Content Lake.
Use case: When a pestReport is created with severity "high" or "critical", automatically fetch weather conditions for the field and append a risk note to the pest report's recommendedAction.
Sanity webhook config:
• Filter: _type == "pestReport" && severity in ["high", "critical"]
• Trigger: Create
• Projection: { _id, field->{farm->{coordinates}}, severity, pest }
Logic:
1. Receive webhook payload.
2. Validate webhook signature (Sanity webhook secret).
3. Fetch 7-day forecast for the field's coordinates.
4. Check if humidity > 80% or temperature > 30C (conditions favouring pest spread).
5. Patch the pestReport document: append weather risk assessment to recommendedAction.
This is the "external API call triggered by a workflow event" the challenge specifically rewards.

Seed script

My Build Process (the heart of the submission):
Structure the writeup around these beats:
1. Why this domain. "I work in IT at a South African agricultural company. I wanted to build something from a world I actually know, not another blog template." This is the hook. It explains why the schema is thoughtful rather than generic.
2. Schema design decisions. Walk through the content model. Why season is the core document. Why weatherSnapshot is its own type rather than embedded. Why stageHistory is an array on the season rather than separate documents. Show the schema relationship diagram.
3. The workflow state machine. Explain the stage lifecycle. Show the transition table. Explain guards and why they matter (you can't harvest if you haven't set a harvest date). Show a real guard failure and how it surfaces in the UI.
4. Weather integration as a side effect. This is the "external API call triggered by workflow" the challenge wants. Explain how Open-Meteo is called on stage transitions. Show a real weatherSnapshot document in Sanity. Explain the summary computation.
5. The pest report webhook. Explain the automated risk assessment flow. A critical pest report triggers a weather check to see if conditions favour spread.
6. What broke. Be honest. What prompts failed in Claude Code? What did you have to fix by hand? What would you do differently? This is what the judges are looking for in Path Two.
Sanity Project Details: Include the project ID and a link to the public dataset.
Agent Session: Embed the Claude Code transcript. Curate it to show the interesting parts: schema design prompts, workflow debugging, weather integration. Make sure it's set to public.
